You are consolidating and solidifying an Android project called Chameleon / HTML Realizer.

PRODUCT AIM

This is not merely a WebView wrapper and not a fixed-purpose automation app. It is an Android "app-making app": the user installs one APK, writes or loads HTML/JavaScript, and turns that HTML/JS into a capable Android application without recompiling the APK.

The intended architecture has two layers:

1. A small, trustworthy native Kotlin shell that owns the controls and Android entry points that must remain available even if the loaded HTML is blank, broken, hostile, navigated away, stuck in a JavaScript loop, or crashes the WebView renderer.
2. A general JavaScript-to-Android capability runtime. Most app-specific UI, rules, automation, and behavior belong in HTML/JS. Kotlin should provide general reflection, lifecycle, permission, background, and OS-component gateways rather than hardcoding each future app.

The design goal is "origami": a few composable primitives should unfold into many capabilities. Extend existing argument-driven pipes instead of creating a separate wrapper system for every feature.

BRIDGE, SANDBOX, AUTHENTICATION, AND POLICY MUST BE DISTINCT

Do not collapse Bridge ON/OFF, Sandbox ON/OFF, authentication, and the three reflection lists into one ambiguous trust button.

Required state semantics:

1. Bridge OFF
   - All privileged JavaScript-to-native operations are disabled regardless of sandbox or password state.
   - Every native bridge entry point must enforce the master state; security must not depend on merely deleting a JS property.
   - Turning the bridge off immediately bumps/revokes the active epoch and releases page-owned handles, leases, callbacks, proxies, queued deliveries, temporary hosts, and service registrations created for that epoch.
   - Existing HTML/JS and the default Realize action continue to work as ordinary WebView content.
   - If physical removeJavascriptInterface/addJavascriptInterface requires a reload to become visible, still enforce the native gate immediately and document the reload behavior.

2. Bridge ON + Sandbox ON
   - The bridge may expose only minimal non-privileged status/version information.
   - Reflection, Android service ports, accessibility, notifications, files, sensors, alarms, vibration, MediaProjection, activity launching, and similar privileged operations return a stable security error such as E:SEC.
   - No stale handle or previously authorized page may bypass the sandbox.

3. Bridge ON + Sandbox OFF
   - If a password is configured, the current document/session must authenticate before privileged calls are accepted.
   - Once authenticated, every Java and Kotlin reflection operation passes through the same policy engine described below.
   - A new external navigation/document trust boundary resets authentication, page epoch, handles, callbacks, queued events, and temporary grants. Do not let unrelated newly loaded content inherit an earlier page's authority.

4. Cut HTML Internet is independent of all three states above.

Persist user-selected global settings where appropriate, but do not persist per-document authentication, handles, callbacks, temporary approvals, or ephemeral trust across unrelated documents/process recovery.

BLACKLIST / GRAYLIST / WHITELIST

Implement all three as real native-editable policy lists. Do not preserve an accidental inversion of the old list names.

Use this deterministic meaning and precedence:

1. Blacklist match: hard deny. Blacklist wins over every other matching rule.
2. Whitelist match: allow without a prompt, provided Bridge is ON, Sandbox is OFF, and authentication requirements are satisfied.
3. Graylist match: show the native decision dialog.
4. No match: prompt by default rather than silently allowing an unknown operation. A deliberate Whitelist entry such as ALL may be used to request unrestricted reflected power.

The native decision dialog must provide:

- Allow once: permit only this request and do not persist the decision.
- Always allow: add the selected canonical scope to Whitelist and execute.
- Block: add the selected canonical scope to Blacklist and deny.
- Cancel/back/dismiss: deny without changing a list.

Canonicalize requests before matching. Include at least operation kind, declaring class, member/property/field/constructor name, and resolved signature where known. Support useful scopes such as ALL, package, class, member, and full signature without relying only on accidental substring collisions. Make matching case/normalization behavior explicit.

If legacy stored entries have different historical semantics, migrate or present them explicitly. Never silently reinterpret a saved allow as a deny or vice versa. Report the migration decision.

Java reflection and Kotlin reflection must use the same Blacklist/Graylist/Whitelist evaluation and the same audit/log path. A Kotlin-reflection route must not bypass a Java-reflection denial, and vice versa.

CUT HTML INTERNET: EXACT SCOPE

Add a native toggle labeled clearly as "Cut HTML Internet" or "Cut HTML Internet (WebView only)."

When ON, it should block Internet requests initiated through normal HTML/WebView mechanisms as completely as the WebView APIs reasonably permit, including:

- Top-level http/https navigation.
- fetch and XMLHttpRequest.
- Remote scripts, stylesheets, images, media, fonts, iframes, and subresources.
- Service-worker-controlled requests where the Android WebView API exposes an interception point.
- WebSocket or other renderer network paths if they can be reliably controlled without pretending an ineffective hook is a security boundary.

Keep local editor/runtime schemes working, including the local base origin and required data/file/content/blob/about behavior where appropriate.

The native Internet Exceptions list must:

- Allow exact hosts and their subdomains only by documented matching rules.
- Normalize case, whitespace, leading dots, trailing dots, and IDN representation deliberately.
- Avoid false matches such as evil-example.com matching example.com.
- Apply consistently to top-level and subresource WebView requests.
- Support temporary session exceptions separately from persisted exceptions if the runtime already has both concepts.

Critical intended limitation: this toggle controls HTML/WebView-originated Internet paths only. It must deliberately ignore Internet access performed through the enabled reflection bridge, such as reflected java.net APIs, sockets, platform networking services, or a reflected HTTP client. Do not add reflection-class blocks merely because Cut HTML Internet is ON. Reflection-originated networking remains governed by Bridge ON/OFF, Sandbox/authentication, Blacklist/Graylist/Whitelist, Android permissions, and platform restrictions.

This means Cut HTML Internet is not a device firewall and is not a security boundary against HTML that has already been granted unrestricted reflection. State that accurately in native UI/help and in the test report. Also do not unnecessarily block the native shell's own lifecycle/control operations.

Measure the real coverage of WebView interception. If a renderer path such as WebSocket cannot be reliably blocked by the available WebView hooks, report that exact limitation instead of claiming total isolation. Prefer a compact native solution; do not add a large networking stack solely to simulate a firewall unless the user explicitly approves it.

GENERAL REFLECTION BRIDGE

Preserve the original legacy K.* JavaScript facade for zero regression, but implement it as a compatibility facade over one generalized core. Also preserve and improve I's generalized K.q-style route. Do not maintain two independent heaps, security systems, callback systems, or overload resolvers.

The unified bridge must support, where Android/platform restrictions permit:

- Class lookup.
- Constructor calls.
- Static and instance method calls.
- Public field get/set and array construction retained from the original bridge.
- Kotlin functions, properties, constructors, object/companion access, and Kotlin-specific callable/property operations when kotlin-reflect provides real additional capability.
- Reliable overload selection using typed coercion and deterministic scoring.
- Primitive/boxed values, nullability, enums, chars, numeric conversions, arrays, and varargs.
- Object handles with explicit retain/release.
- Epoch-scoped handles so stale pages cannot reuse old objects.
- Interface proxies and asynchronous callbacks/events into JS.
- Stable error codes plus inspectable underlying exception information.
- Activity/main-thread dispatch where Android requires it.
- General live ports such as app context, current Activity, WebView, accessibility service, notification listener, runtime service, projection, and other active Android entry points.
- Port-ready/closed lifecycle events.
- Bounded event queues, drop accounting, cleanup, and no unbounded object retention.
- Renderer recovery and Activity re-parenting without parallel WebViews unless a separately justified capability truly requires one.

Kotlin reflection is required, but do not add it cosmetically. Demonstrate at least one Kotlin-only or Kotlin-better operation that Java reflection does not model cleanly. Quantify the release APK size cost of kotlin-reflect and any other dependency. If a lighter architecture can supply the requested Kotlin capability without losing it, explain and use it. Do not sacrifice readable role-bearing identifiers or create lexical minification merely to reduce size.

Reflection does not bypass Android permissions, manifest declarations, hidden-API enforcement, scoped storage, MediaProjection consent, accessibility enablement, notification-listener enablement, root/ADB boundaries, or secure/protected content. Report these as platform limits, not bridge bugs.

ANDROID CAPABILITY PORTALS

Keep Kotlin code generic and small, but add native portals wherever Android requires a declared component, user-consent flow, lifecycle owner, callback receiver, or foreground-service type. All portals should feed the same port/event/epoch machinery rather than parallel ad-hoc bridges.

Priority capabilities:

1. Accessibility screen understanding and control
   - Return a structured screen/window tree, not only text|centerX|centerY.
   - Include text, content description, view ID, package/class, bounds, state flags, actions, child relationships, window metadata, and enough identity to find a node again safely.
   - Emit accessibility events to JS.
   - Click by node/action and by coordinate.
   - Support long press, swipe, scroll, multi-stroke gestures, text entry/setText, focus, and global actions.
   - Handle stale nodes and recycled AccessibilityEvent/AccessibilityNodeInfo objects correctly.
   - Support accessibility screenshots where available and MediaProjection for continuous/visual capture where necessary.

2. Event-driven automation
   - Notification posted/removed/ranking events.
   - Dynamic BroadcastReceiver registration and completion.
   - ContentObserver and FileObserver events.
   - Activity results and runtime-permission results.
   - Time/alarm triggers.
   - Foreground/background runtime sufficient for user-authored JS to wait for conditions under Android's actual background limits.

3. Actions needed for practical automations
   - Vibration with API-appropriate fallbacks.
   - Alarm/notification behavior when a JS condition becomes true.
   - Exact-alarm capability only through the required permission/special-access path, with a documented inexact fallback when unavailable.
   - Intents, app launching, clipboard, files/content URIs, sensors, camera, microphone, location, and networking through the general bridge where permitted.

4. Screen capture
   - Correct MediaProjection consent and foreground-service lifecycle.
   - Resize, visibility, stop, and error events.
   - No reuse of invalid consent tokens or stale projections.

The intended proof scenario is that HTML/JS can observe another app's screen or notifications, evaluate a condition, click/gesture when appropriate, and trigger vibration or an alarm, while the native shell remains recoverable.

PERSISTENCE, LIFECYCLE, AND RECOVERY

- Prefer one persistent runtime WebView that can be safely re-parented between application/runtime context and Activity, if testing confirms it remains correct.
- Do not create one Activity WebView plus another service WebView with separate bridge state unless a measured limitation makes that unavoidable.
- Configuration change, Activity recreation, Activity close/reopen, renderer death, background/foreground transition, and service reconnect must not duplicate the runtime or leak the old Activity.
- Page/navigation changes must revoke page-owned authority and objects at the correct trust boundary.
- Retained Android callback objects must be released/unregistered when their epoch ends.
- A foreground service must be started only through legal timing paths, publish its notification promptly, and stop cleanly.
- Process death is allowed to end in-memory JS state, but reopening the app must always recover to a usable native shell/editor rather than a blank/bricked state.
